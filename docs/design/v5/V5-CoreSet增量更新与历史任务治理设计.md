# V5 CoreSet 增量更新与历史任务治理设计

更新时间：`2026-05-12`

## 1. 背景

在 `V4.10` 之后，系统已经具备：

- 全量题目 embedding 落库与可视化
- CoreSet 全量异步选题
- 题池治理、批次撤回与历史任务查看

但对照早期设计建议，仍存在两个需要补强的点：

1. 新数据导入后，如果直接每次全量重算，会带来不必要的计算开销。
2. 管理后台虽然能看到批次结果，但还需要把“任务本身”的运行阶段、失败原因、基线与增量上下文展示清楚。

因此，V5 将 CoreSet 能力进一步收口为：

- 全量选题：建立正式基线
- 增量更新：只处理基线之后新增且仍未标注的题
- 历史任务治理：可追踪、可解释、可定位失败

## 2. 设计目标

本轮设计目标如下：

1. 现有数据保持不变，不因为新数据导入而强制重算整个历史题池。
2. 新导入题目一旦入库，优先增量补齐 embedding。
3. 管理员可以明确区分“全量选题”和“增量更新新导入题”。
4. CoreSet 历史任务需要展示：
   - 运行状态
   - 当前阶段
   - 失败原因
   - 全量/增量模式
   - 基线批次
   - 聚类统计

## 3. 增量更新策略

### 3.1 基线定义

系统把最近一次成功的 CoreSet 任务视为当前基线。基线会记录：

- `baseline_run_id`
- `baseline_run_no`
- `baseline_batch_no`
- `snapshot_created_before`

其中 `snapshot_created_before` 表示该次 CoreSet 实际纳入候选集合的时间水位。后续增量更新时，只会处理：

- `created_at > snapshot_created_before`
- 仍然处于 `PENDING`
- 题干可用
- `source_status = ACTIVE`

这意味着：

- 历史老题不动
- 已经进入待标注/已标注流转的题不动
- 新导入且仍未标注的题，才进入增量 CoreSet 候选池

### 3.2 导入后的 embedding 维护

导入流程保持“业务写库优先、embedding 异常不阻断导入”的原则，同时补充了增量保障：

1. 新题创建后尝试批量补 embedding。
2. 批量导入时对本批次新增/归一化后的题目统一调用 embedding 生成。
3. 导入页完成后会联动刷新主动学习概览，管理员能立即看到新的增量候选数量。

因此，增量 CoreSet 默认优先复用数据库中已有向量，而不是再次从文本临时构造表示。

### 3.3 历史锚点集合

增量更新不是只看“新增题之间谁更代表”，还要考虑“新增题相对于已有代表题是否真的补充了覆盖”。

为此，系统会为增量模式构建一组锚点：

- 取同一候选范围下历次成功 CoreSet 任务的已选代表题
- 对题目去重
- 读取这些题的 embedding 作为历史锚点集合

锚点集合的作用是：

- 避免新批次总是选到与历史已选代表题高度重复的题
- 让增量更新更偏向“补覆盖缺口”，而不是简单重复全量策略

### 3.4 不同策略的增量实现

#### K-Means

`kmeans` 增量模式采用：

1. 仅对新增候选题聚类
2. 用历史锚点衡量每个新增簇的“新颖度”
3. 按“簇规模 × 新颖度”分配配额
4. 每个簇内优先选择最接近局部中心、同时相对锚点更有补充价值的题

这样做保留了 K-Means 的代表性，同时不会重新扰动历史题池。

#### Facility Location / Graph Cut / MoE

这三种策略在增量模式下统一采用“分层全量 + 锚点约束”的形式：

1. 只对新增候选题做局部聚类
2. 先根据簇规模与簇新颖度分配预算
3. 簇内选择时把历史锚点作为参考集合
4. Facility Location 通过“相对于锚点仍能带来多少新增覆盖”来计算边际收益
5. Graph Cut 在代表性之外加入“避免与锚点过近”的惩罚
6. MoE 延续 `FL + GC` 的混合选择逻辑

#### Random

随机策略也支持增量模式，但只在“新增题集合”内随机抽样，用于对照实验。

## 4. 管理后台交互设计

### 4.1 为什么采用按钮而不是自动触发

本轮没有把“新题导入后自动执行增量 CoreSet”做成默认行为，而是增加了管理员可见、可控的按钮：

- `开始选题`：执行一次全量 CoreSet
- `增量更新新导入题`：仅对基线之后新增的未标注题执行增量 CoreSet

这样设计的原因是：

1. 管理员需要先确认导入质量、判重与 embedding 状态。
2. 某些批次导入后，可能并不希望立即进入待标注池。
3. 增量更新属于治理动作，最好具备明确的人为触发痕迹和任务记录。

### 4.2 管理员界面显示

CoreSet 区域会额外展示：

- 当前增量基线批次
- 当前待增量更新题数
- 历史锚点数
- 快照截止时间

这样管理员在点击按钮前，就能知道：

- 是否已经存在基线
- 现在是否真的有新增题需要处理
- 这次增量更新会建立在什么历史上下文之上

### 4.3 历史任务列表与详情

历史任务列表新增或强化展示：

- 策略
- 更新模式（全量 / 增量）
- 候选数、选中数、入池数
- 当前阶段
- `selection_mode`

详情抽屉中进一步展示：

- 失败原因
- 运行阶段
- 基线批次
- 历史锚点数
- 快照截止时间
- 簇数量 / 非空簇数量 / 最大簇规模 / 最小簇规模

## 5. 当前实现边界

本轮实现的重点是把“增量更新”正式纳入现有系统闭环，而不是一次性做成最终最复杂的研究版。

当前边界如下：

1. 增量候选的判定水位基于题目创建时间与基线快照。
2. 基线锚点来自历史成功 CoreSet 任务的已选代表题。
3. 导入匹配到历史旧题但未新建 `question` 的情况，不会被视为“新增题”。
4. 当前没有额外引入 Faiss / HNSW 常驻索引，仍以数据库向量 + 后台任务为主。

这些边界足以支撑当前项目阶段的“新数据导入后增量补选题”需求，同时不破坏已有数据状态。

## 6. 已完成项

截至 `2026-05-12`，已完成：

- CoreSet 后台任务支持 `full / incremental`
- `kmeans / facility_location / graph_cut / moe / random` 全部接入正式增量路径
- 导入后 embedding 增量补全继续沿用
- 导入页联动刷新主动学习概览
- 管理后台新增增量基线摘要与“增量更新新导入题”按钮
- CoreSet 历史任务与详情展示更新模式、失败原因和聚类统计

## 7. 后续建议

后续可以继续往下推进三类增强：

1. 指标在线化  
把 CoverageRadius、AMS、Redundancy、CRR、MMD 等质量指标落到 `metrics_json`。

2. 更强的近邻基础设施  
当题量继续增长时，引入 Faiss / HNSW 做近邻搜索与局部更新加速。

3. 自动策略建议  
结合已标注规模、最近训练效果和历史批次表现，自动推荐当前更适合全量还是增量，以及更合适的算法。
