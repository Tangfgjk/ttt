# V2 实施设计文档

## 1. 文档目标

本文档在 `V1` 设计基线上，结合 3 份样例数据源的真实字段，给出可直接进入开发阶段的 `V2` 落地方案，覆盖：

- 最终表结构
- 模块边界与模块接口
- API 清单
- 项目目录结构
- 第一阶段开发任务拆分

本版设计的关键约束如下：

- 主数据库先使用 `MySQL 8`
- 系统先采用 `模块化单体 + Redis + Celery` 架构
- 题库需要支持后续增量导入，不能依赖单一数据源的精简字段
- 数据库设计遵循三大范式，避免将题目、标注、考试作答混装到一张大表

## 2. 样例数据集分析与字段并集

### 2.1 数据集角色判断

本次设计参考了以下 3 个样例文件：

- `C:/Users/29694/Desktop/初中.xlsx`
- `C:/Users/29694/Desktop/0A1Hq4pYlG1VSNZaD7V.json`
- `C:/Users/29694/Desktop/工作簿1.xlsx`

它们分别对应 3 种不同粒度的数据：

1. `初中.xlsx`
   - 已完成核心素养与认知层级标注
   - 题目字段较少
   - 更适合作为“已标注题库”或“金标准标签数据”

2. `0A1Hq4pYlG1VSNZaD7V.json`
   - 是单题粒度的题目元数据
   - 包含题目基础属性、知识点标签、教材目录、答案、解析、题型、难度等
   - 更适合作为“题库主数据源”的结构参考

3. `工作簿1.xlsx`
   - 不是纯题库表，而是“考试 + 题目 + 学生作答明细”的明细数据
   - 同一题会随不同学生重复出现
   - 适合作为“考试测评数据源”，不能直接并入题目主表

### 2.2 三个数据源的字段并集

按业务域拆解后，字段并集如下。

| 业务域 | 来源字段 |
|---|---|
| 题目标识 | `初中题目id`、`exerciseID`、`题目ID` |
| 题目正文 | `试题内容`、`question`、`题目内容`、`题干（子题）` |
| 学科年级 | `subjectCategory`、`测试学科`、`gradeIndex`、`gradeLevel`、`gradeName`、`测试年级`、`年级编号` |
| 题型与难度 | `baseTypeIndex`、`exerciseType`、`blankCount`、`题型标签`、`难度标签` |
| 答案与解析 | `queAns`、`solution`、`题目答案`、`子题答案` |
| 知识点与目录 | `知识点`、`tags.*`、`queCtlgs.*`、`知识点标签`、`知识点ID`、`章节标签`、`章节标签ID` |
| 标注标签 | `认知层级水平` 下的 `识记/理解/应用/分析/综合/评价`，`核心素养` 下的 9 个素养列 |
| 题目扩展属性 | `subQueNum`、`subQues`、`has_sub_questions`、图片/MathML/HTML 内容 |
| 考试维度 | `测试时间`、`测试名称`、`测试类型`、`测试总分`、`考试ID`、`考试编号`、`学期` |
| 班级维度 | `测试班级`、`班级编号`、`班级序号` |
| 学生维度 | `学生编号` |
| 作答维度 | `测试得分`、`学生作答`、`题目得分`、`题目分值` |

### 2.3 并集后的设计原则

基于三范式，不能把上面的字段都堆到 `questions` 一张表里。V2 采用以下拆分原则：

- 题目主数据与考试作答数据分离
- 题目本体与知识点、目录、外部来源、标签结果分离
- 已标注数据与人工标注流程数据分离
- 保留原始导入记录，既支持未来字段扩展，也便于增量同步

### 2.4 统一字段映射结论

| 原始字段域 | 目标表 |
|---|---|
| 题目基础属性 | `questions`、`question_contents` |
| 外部题目编号与原始 payload | `question_external_refs`、`source_question_records` |
| 知识点体系 | `knowledge_points`、`question_knowledge_points` |
| 教材目录体系 | `catalogs`、`question_catalogs` |
| 已有金标准标签 | `question_gold_labels`、`question_gold_competencies` |
| 考试/班级/学生/作答 | `exams`、`classes`、`students`、`exam_questions`、`student_exam_scores`、`student_question_responses` |
| 系统人工标注 | `annotations`、`annotation_competencies`、`annotation_knowledge_points` |

### 3.4 MySQL 约束下的落地约定

- 字符集统一使用 `utf8mb4`
- 业务主键统一使用 `BIGINT`
- 原始导入记录使用 `JSON` 存储 `raw_payload`
- 不把知识点、目录、核心素养直接塞进题目表的 `JSON` 中
- 向量暂存在 `question_embeddings.vector_json` 与本地 `Faiss` 索引文件中

## 4. 模块设计

### 4.1 模块划分

1. `auth`
   - 用户、角色、权限、登录、培训准入

2. `dictionary`
   - 学科、年级、题型、认知层级、核心素养、知识点类型、教材目录等基础字典

3. `question_bank`
   - 题目主数据、题目内容、题目来源映射、知识点挂接、目录挂接、增量导入

4. `assessment`
   - 考试、班级、学生、试卷题目、学生作答与成绩

5. `annotation`
   - 题目领取、标注提交、版本记录、聚合、一致性、争议复核

6. `embedding`
   - 文本向量计算、缓存、降维、Faiss 索引维护

7. `coreset`
   - 推荐批次、推荐明细、算法配置、实验日志、质量指标

8. `training`
   - 训练任务、模型版本、训练指标、训练数据版本

9. `admin_analytics`
   - 管理后台、数据看板、导入任务监控、系统审计

### 4.2 模块间依赖

- `question_bank` 依赖 `dictionary`
- `assessment` 依赖 `question_bank`、`dictionary`
- `annotation` 依赖 `question_bank`、`auth`
- `embedding` 依赖 `question_bank`
- `coreset` 依赖 `embedding`、`annotation`
- `training` 依赖 `annotation`、`question_bank`
- `admin_analytics` 依赖所有业务模块的聚合读模型

## 9. 第一阶段开发任务拆分

### 9.1 第一阶段目标

第一阶段不追求把推荐、训练、可视化一次做完，而是先完成“可稳定导入、可查询、可标注、可聚合”的主链路。

阶段目标：

- 建好 MySQL 基础表
- 打通 3 类数据源的导入链路
- 搭好登录和权限
- 打通题库检索、标注提交、3 人聚合的业务闭环

### 9.2 第一阶段实施顺序

#### 任务 1：定稿基础字典与数据库迁移

- 建 `subjects`、`grades`、`question_types`、`cognitive_levels`、`competencies`
- 建 `knowledge_types`、`knowledge_points`、`textbooks`、`catalogs`
- 完成 Alembic 初始迁移

这是第一步，优先级最高。

#### 任务 2：完成导入底座

- 建 `data_sources`、`import_batches`、`source_question_records`
- 写 3 个导入器：
  - `dataset1_labeled_importer`
  - `dataset2_json_importer`
  - `dataset3_exam_importer`
- 先落原始记录，再做归一化解析

#### 任务 3：完成题库主表与增量同步

- 建 `questions`、`question_external_refs`、`question_contents`
- 建 `question_subquestions`、`question_assets`
- 建 `question_knowledge_points`、`question_catalogs`
- 支持按外部 ID 幂等更新

#### 任务 4：完成已标注金标准导入

- 建 `question_gold_labels`
- 建 `question_gold_competencies`
- 将 `初中.xlsx` 中的一热标签映射为规范化标签记录

#### 任务 5：完成考试测评落表

- 建 `classes`、`students`、`exams`、`exam_questions`
- 建 `student_exam_scores`、`student_question_responses`
- 支持从 `工作簿1.xlsx` 去重出题目，再入考试作答数据

#### 任务 6：搭后端基础骨架

- FastAPI 项目初始化
- 配置、日志、异常、JWT、RBAC
- SQLAlchemy Model、Repository、Service 分层

#### 任务 7：完成标注业务最小闭环

- 建 `annotation_tasks`、`annotations`
- 建 `annotation_competencies`、`annotation_knowledge_points`
- 建 `question_label_aggregates`、`question_aggregate_competencies`
- 完成：
  - 题目领取
  - 草稿保存
  - 提交标注
  - 3 人完成判定
  - 聚合结果生成

### 9.3 第一阶段暂不做

- 不先做复杂的在线增量 Coreset
- 不先做复杂训练编排
- 不先做大屏可视化
- 不先做多模型自动切换

这些放到第二阶段更稳妥。

## 11. 数据库字段变更规范

为了保证项目在 0 到 1 过程中可以持续调整字段，又不把数据库演进搞乱，后续所有表结构变更统一遵循以下规范。

### 11.1 基本原则

- 所有数据库结构变更必须通过 `Alembic` 迁移执行
- 禁止直接在线手改生产或共享开发库表结构
- 优先做“向后兼容”的变更，再做代码切换，最后再清理旧字段
- 能新增字段解决的问题，不优先用破坏性修改
- 对不确定、可能继续扩展的内容，优先新增关联表，而不是持续膨胀主表

### 11.2 允许快速迭代的变更类型

以下变更视为常规迭代，可正常进入版本开发：

- 新增普通字段
- 新增索引
- 新增非核心关联表
- 新增字典项或状态枚举值
- 新增可空字段
- 给 JSON 原始记录增加解析映射逻辑

### 11.3 需要评审后再做的变更类型

以下变更会影响面较大，实施前需要先更新设计文档并确认迁移方案：

- 修改主键或外键策略
- 修改唯一约束
- 把可空字段改为非空字段
- 删除字段
- 修改高频查询字段的数据类型
- 拆分核心业务表
- 调整题目、标注、推荐、训练之间的主关联关系

### 11.4 推荐的字段变更流程

1. 先更新设计文档
   - 明确为什么改
   - 明确影响哪些模块、哪些 API、哪些历史数据

2. 再写迁移脚本
   - 使用 `Alembic` 增量迁移
   - 迁移脚本必须可重复执行、可回滚

3. 再改后端模型和接口
   - 更新 `SQLAlchemy` 模型
   - 更新 `Pydantic` Schema
   - 更新服务层与 API

4. 最后补数据修复和验证
   - 对历史数据做回填
   - 校验索引、唯一约束、默认值
   - 验证主要查询与写入链路

### 11.5 推荐采用的兼容式变更方式

#### 新增字段

推荐方式：

- 先加可空字段或带默认值字段
- 代码兼容新旧逻辑
- 数据回填后再决定是否改为非空

#### 重命名字段

不建议直接重命名，推荐分 3 步：

1. 新增新字段
2. 代码双写或迁移旧数据
3. 稳定后删除旧字段

#### 删除字段

不建议直接删，推荐分 3 步：

1. 先在代码中停用
2. 观察一到两个版本确认无依赖
3. 再通过迁移脚本删除

#### 字段类型调整

推荐方式：

1. 新增目标类型字段
2. 分批迁移旧数据
3. 代码切换读取逻辑
4. 最后清理旧字段

### 11.6 各类表的变更建议

#### `questions`、`annotations`、`training_tasks`

这类核心主表应保持稳定：

- 不频繁加杂项字段
- 新扩展优先走关联表
- 避免把实验性字段直接塞入主表

#### 字典表

这类表可以平稳扩展：

- 可以新增枚举项
- 尽量少改已有编码值
- `code` 一旦对外使用就不轻易改名

#### 原始导入表

这类表允许更灵活：

- `raw_payload` 保留原文
- 新增解析字段时不影响历史原始记录
- 适合作为未来字段变化的缓冲层

### 11.7 版本管理建议

- 每次表结构变更都在 `docs/design/v2/` 或后续版本文档中记录
- 重大变更单独新增“数据库变更说明”
- 迁移脚本名称应能看出用途，例如：
  - `add_question_source_version`
  - `create_annotation_review_tables`
  - `split_exam_response_tables`

### 11.8 当前阶段的实际结论

在本项目当前阶段，后续如果发现字段不合适，通常都可以比较平滑地处理，尤其是下面这几类：

- 补充题目元数据字段
- 增加导入映射字段
- 增加标注附加信息字段
- 增加推荐日志与训练日志字段
- 拆出新的中间关联表

只要坚持：

- 先改文档
- 再写迁移
- 再改模型和接口
- 最后做数据校验

后续数据库演进就是可控的，不会失控。

## 12. 最终实施结论

V2 的第一步不是直接写页面，而是先做下面三件事：

1. 定稿字典表与主业务表
2. 打通三类数据源的原始导入与规范化入库
3. 搭出“题库查询 + 人工标注 + 聚合结果”最小闭环

如果这三步先完成，后面的推荐、训练、可视化都可以在稳定的数据底座上继续迭代，而不会反复返工。
