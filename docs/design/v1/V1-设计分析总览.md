# V1 设计分析总览

## 1. 文档定位

这组设计文档描述的是一个“初中数学题核心素养标注系统”的 V1 方案，核心目标是：

- 支持多人协作的试题标注流程。
- 以 3 名不同标注员独立标注作为完成标准。
- 在 4 万级未标注题库上引入 Coreset Selection，实现主动学习式推荐。
- 用嵌入计算、可视化和训练闭环验证推荐策略是否优于随机采样。

从完整度上看，这批文档已经覆盖了：

- 系统架构
- 数据模型
- 核心对象设计
- 核心页面设计
- Coreset 策略与实验建议

因此适合作为项目的第一版设计基线保存。

## 2. V1 系统范围

结合 5 份文档，V1 的业务范围可以归纳为以下几个核心子系统：

### 2.1 标注业务主链路

- 用户注册、登录、培训与准入。
- 试题列表浏览、领取、标注、提交。
- 同一题目的多标注员协作与状态跟踪。
- 标注完成后触发聚合、质量评估与后续训练。

### 2.2 智能推荐与主动学习

- 基于题目嵌入向量进行 Coreset 选择。
- 支持 `k-means`、`herding`、`FL`、`GC`、`uncertainty` 等算法。
- 面向不同标注阶段切换不同推荐策略。
- 支持混合策略和未来自适应算法选择。

### 2.3 模型训练闭环

- 标注数据沉淀为训练样本。
- 模型训练任务异步执行。
- 训练结果作为下一轮推荐的辅助输入。
- 通过学习曲线验证主动学习策略效果。

### 2.4 可视化与管理后台

- 试题嵌入的二维降维展示。
- 推荐结果、标注进度、训练任务和质量指标看板。
- 管理员对用户、题库、训练任务和算法配置的管理。

## 3. 各文档价值判断

### 3.1 `01-系统架构设计.md`

这是整个 V1 的总纲文档，给出了：

- 四层结构：前端、应用服务层、数据层、计算资源层。
- 技术建议：FastAPI/Flask、Celery、Redis、PostgreSQL、MinIO/S3、向量检索。
- 核心设计原则：插件化、抽象接口、事件驱动、增量更新、异步化。

它的作用是定义“系统应该长成什么样”，适合作为后续技术拆分的上位文档。

### 3.2 `02-ER图设计.md`

这份文档把业务实体拆得比较完整，关键表包括：

- `users`
- `roles`
- `questions`
- `annotations`
- `question_competency_labels`
- `question_embeddings`
- `recommendations`
- `coreset_logs`
- `training_tasks`
- `learning_records`

它说明这个项目不只是“标注平台”，而是一个同时包含训练、推荐、实验记录和用户学习闭环的系统。

### 3.3 `03-类设计.md`

这份文档体现了较强的工程化意识，尤其是：

- `BaseCoresetSelector`
- `CoresetAlgorithmFactory`
- `BaseEmbedder`
- `EmbeddingService`
- `RecommendationEngine`
- `AnnotationService`
- `TrainingService`
- `EventBus`

这意味着作者已经不满足于“页面和表结构”，而是在为后续可维护代码结构做准备。

### 3.4 `04-UI设计.md`

这份文档对页面角色划分很清晰，核心页面包括：

- 登录/注册
- 培训页
- 标注页
- 可视化页
- 训练监控页
- 管理后台

其中标注页和可视化页是系统体验的核心，说明 V1 不只是后台流程系统，也强调研究展示与可解释性。

### 3.5 `05-CoresetSelection系统设计建议.md`

这是最有研究特色的一份文档，包含：

- 各种 Coreset 算法实验指标对比
- 冷启动 / 成长期 / 成熟期的推荐策略
- 混合算法设计
- 增量更新策略
- 在线评估指标
- 与模型训练的主动学习闭环

它直接决定了系统的“研究亮点”和差异化价值。

## 4. 我对 V1 的整体判断

### 4.1 优点

- 业务目标清晰，研究场景和工程场景结合得比较自然。
- 文档覆盖面完整，已经形成“架构-数据-类-界面-算法”的五层闭环。
- 把 Coreset 设计成可插拔模块，这是后续研究迭代的正确方向。
- 对多人标注、一致性、实验对比和训练闭环都有考虑，不是单点设计。

### 4.2 当前最适合的定位

更准确地说，这套文档当前最适合作为：

- 原型开发前的 V1 方案
- 课题/研究型系统的设计基线
- 后续技术实现与版本回写的参考基准

它已经足够支撑下一阶段的系统拆解，但还没有细到可以直接无歧义开工全部模块。

## 5. 当前设计中的关键待定项

下面这些点不是“问题”，但它们需要在 V2 里被定稿，否则实现阶段会反复返工。

### 5.1 技术选型仍有分叉

- 前端写成了 `React/Vue3 + TypeScript`，但最终必须二选一。
- 后端写成了 `FastAPI / Flask`，但由于涉及异步任务、Pydantic、类型定义和接口文档，实际更推荐直接定为 `FastAPI`。
- 数据库主库在文档中是 `PostgreSQL`，这与当前你本机已配置的 `MySQL` 环境并不一致。

建议：

- 若项目强调向量检索、JSONB、训练实验记录，优先使用 `PostgreSQL + pgvector`。
- 若短期只是做业务原型，也可以先用 `MySQL`，但需要同时重新审视 `JSONB`、向量字段和数组字段设计。

### 5.2 数据模型还存在“可选写法”

例如文档中多处写法仍是“二选一”：

- `UUID / BIGINT`
- `vector(768) / JSONB / BYTEA`
- 向量库 `Qdrant/Milvus` 为可选

这类写法适合设计初稿，不适合实施。V2 需要将这些可选项落为唯一方案。

### 5.3 状态机与并发规则还不够细

当前已定义：

- `PENDING`
- `ANNOTATING`
- `COMPLETED`

但还缺少更细的业务规则，例如：

- 一个题目被某人打开但未提交时是否加锁。
- 多人同时标注时如何避免“重复领取”与“重复推荐”。
- 出现争议时是否进入 `DISPUTED` 或 `REVIEW_REQUIRED`。
- 标注修改是否覆盖历史版本，还是始终追加版本。

### 5.4 接口层还缺少合同化设计

当前只定义了“REST + WebSocket”的风格，但没有定义：

- 关键 API 列表
- 请求/响应 DTO
- 分页、过滤、排序规范
- 鉴权粒度
- WebSocket 事件协议

这部分建议在 V2 中补成接口文档。

### 5.5 训练闭环有方向，但缺少运行约束

训练服务的思路是对的，但工程上还需要明确：

- 哪些任务必须走 GPU。
- 哪些任务可以 CPU 跑。
- 训练任务排队与优先级。
- 模型版本命名规则。
- 模型发布、回滚与对比评估方式。

## 6. 推荐的 V1 基线结论

如果把这套文档作为项目当前阶段的正式设计结论，我建议这样定义 V1：

### 6.1 V1 必须保留的核心能力

- 用户登录、培训、角色管理
- 试题管理与标注流程
- 3 人独立标注完成机制
- 题目嵌入存储与推荐排序
- 至少 2 到 3 种 Coreset 算法接入
- 推荐结果展示
- 基础训练任务管理
- 基础可视化与管理后台

### 6.2 V1 可以延后到 V2 的能力

- 自适应算法选择
- 多目标优化 Coreset
- LLM 预标注
- 在线学习
- 复杂的实验编排系统
- 完整的可视化大屏矩阵

## 7. 建议的 V2 拆解方向

下一版文档建议新增以下内容：

1. `接口设计文档`
   - 明确 API、DTO、状态码和 WebSocket 事件。
2. `技术选型定稿文档`
   - 定死前端框架、后端框架、数据库和向量方案。
3. `状态机与流程设计`
   - 明确题目流转、并发标注、争议处理和任务触发。
4. `部署与配置文档`
   - 明确开发环境、测试环境、生产环境和任务编排方式。
5. `开发任务拆分文档`
   - 将 V1 设计拆为可执行的模块开发任务。
