# V7 Docker Compose 部署设计方案

更新时间：`2026-05-15`

## 1. 文档目的

本文档用于为 K12 学科标注平台设计一套基于 Docker Compose 的部署方案，目标是在不改变当前业务定位的前提下，将本地开发运行模式整理为可供多人共同使用的服务化部署形态。

当前系统已经具备题库导入、判重复核、培训准入、多人标注、争议复核、主动学习选题、训练监控和可视化等主要链路。下一步的重点不是继续补单点功能，而是让这些能力以稳定、可迁移、可维护的方式在服务器上长期运行。

本文档只讨论部署设计，不涉及本轮代码改造实现。

## 2. 当前系统现状

### 2.1 当前运行方式

当前项目主要以本地开发模式运行：

- 前端通过 `vite dev` 提供页面
- 后端通过 `uvicorn --reload` 提供 API
- MySQL、Redis、模型目录、上传目录均依赖本机环境
- Celery Worker 与后台任务尚未被整理为正式常驻服务

这种方式适合单机开发、功能联调和阶段演示，但不适合多人长期协作使用，主要原因包括：

- 服务启动方式偏开发态，缺少正式服务编排
- 本地路径、模型路径、上传路径与个人电脑环境耦合较强
- 多个依赖服务缺少统一生命周期管理
- 数据持久化、备份、日志、重启恢复机制尚未成体系

### 2.2 当前技术栈

系统当前已经具备部署为多服务架构的基础：

| 层次 | 当前技术 |
| --- | --- |
| 前端 | React 18、TypeScript、Vite、Ant Design |
| 后端 | FastAPI、SQLAlchemy、Pydantic Settings |
| 数据库 | MySQL |
| 缓存 / 队列 | Redis |
| 后台任务 | Celery |
| 模型与训练 | PyTorch、Transformers、主动学习任务 |

这意味着项目适合采用“前后端分离 + 后台任务分离 + 数据与文件持久化”的 Compose 编排方式。

## 3. 部署目标与范围

### 3.1 第一阶段目标

第一阶段部署目标是形成一套可用于内网多人协作的服务栈，满足以下要求：

- 多名标注员、复核员、管理员可以通过统一访问地址使用系统
- 前端、后端、数据库、Redis、后台任务服务均可统一启动和管理
- 数据库、上传文件、模型目录和训练产物在服务重启后不会丢失
- 系统具备从一台机器迁移到另一台机器的基础能力
- 后续可以在不推翻架构的前提下继续补鉴权、安全和监控

### 3.2 本轮不追求的目标

本轮部署设计不把以下内容作为立即落地目标：

- 多机高可用
- 云原生弹性扩缩容
- 自动化 CI/CD 全链路
- 训练集群调度
- 公网正式开放前的全部安全加固

也就是说，本方案优先服务于“先把多人协作版稳定跑起来”，再逐步向正式生产版演进。

## 4. 推荐总体架构

### 4.1 服务拓扑

推荐的第一版 Compose 架构如下：

```text
浏览器
  -> Nginx
     -> 前端静态文件
     -> /api -> FastAPI Backend
               -> MySQL
               -> Redis
               -> 持久化卷：uploads / artifacts / models
     -> Celery Worker
        -> MySQL
        -> Redis
        -> 持久化卷：uploads / artifacts / models
```

### 4.2 核心设计思想

这套架构的核心思想是：

- 前端不再以开发服务器形式运行，而是构建为静态资源交由 Nginx 托管
- 后端 API 与 Celery Worker 分离，避免后台重任务拖慢业务请求
- MySQL、Redis 作为独立基础服务，由 Docker 网络统一连接
- 上传文件、训练产物、模型目录全部通过 volume 或宿主机挂载方式持久化
- 所有服务通过 `docker compose up -d` 统一编排和生命周期管理

## 5. 服务拆分设计

### 5.1 nginx

#### 职责

- 对外暴露统一入口
- 托管前端静态资源
- 将 `/api/` 请求反向代理到 FastAPI 服务
- 处理单页应用的路由回退

#### 设计要点

- 暴露 `80` 端口，后续需要时再接入 `443`
- 静态目录指向前端构建产物
- `/api/` 转发到 `backend:8000`
- 对非静态资源请求做 `try_files ... /index.html`，避免刷新前端深层路由时报 404

#### 价值

Nginx 是前端生产部署和统一入口的关键，没有它就仍然停留在本地 Vite 开发代理模式。

### 5.2 backend

#### 职责

- 提供全部业务 API
- 访问 MySQL、Redis
- 读写上传目录和训练产物目录
- 调用模型目录中的 embedding 模型或训练资源

#### 启动方式

第一版建议使用容器内常驻命令启动：

```text
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

后续正式生产化时，可再升级为 `gunicorn + uvicorn worker` 模式。

#### 依赖

- `mysql`
- `redis`
- `.env` 环境变量
- `uploads` 挂载目录
- `artifacts` 挂载目录
- `models` 挂载目录

### 5.3 worker

#### 职责

- 运行 Celery 后台任务
- 承接导入、主动学习、训练、embedding 等异步任务

#### 设计要点

- 与 backend 使用同一份代码镜像
- 仅通过不同的 `command` 区分用途
- 必须单独成服务，不能和 API 共用同一进程

#### 原因

系统未来的导入、训练和主动学习任务具有明显的后台计算特征。如果 worker 与 API 混在一起，会造成：

- 任务高峰时 API 响应变慢
- 导入 / 训练失败后日志难排查
- 服务资源抢占更严重

### 5.4 mysql

#### 职责

- 保存账号、题目、题目状态、标注记录、复核记录、培训记录、训练任务记录等核心业务数据

#### 设计要点

- 使用独立数据卷持久化
- 生产环境不建议直接暴露给公网
- 使用单独数据库用户，不使用 root 直连业务服务
- 需要配合 Alembic 维护表结构演进

### 5.5 redis

#### 职责

- 提供 Celery broker
- 提供 Celery result backend
- 为后续缓存或轻量运行态数据预留能力

#### 设计要点

- 只在 Docker 内部网络使用
- 是否做持久化可按第一版简化，但建议至少保留基础数据目录

### 5.6 frontend-build

前端部署推荐优先采用“构建产物与 Nginx 解耦”的方式，而不是长期保留一个运行中的前端容器。

推荐两种方式：

1. 在发布前构建前端产物，再交给 Nginx 使用
2. 在 Dockerfile 中使用多阶段构建，最终由 Nginx 镜像直接包含 `dist`

对于当前阶段，建议先采用第一种，便于理解和排查；后续成熟后再收敛为单镜像发布。

## 6. 目录与文件组织建议

为避免后续部署资产散落，建议新增部署目录，结构如下：

```text
ttt/
├── backend/
├── frontend/
├── deploy/
│   ├── docker/
│   │   ├── backend/
│   │   │   └── Dockerfile
│   │   ├── frontend/
│   │   │   └── Dockerfile
│   │   └── nginx/
│   │       └── default.conf
│   └── compose/
│       ├── docker-compose.yml
│       └── .env
├── uploads/
├── artifacts/
└── MLM/
```

如果前期希望更轻量，也可以先简化为：

```text
ttt/
├── backend/
├── frontend/
├── deploy/
│   ├── docker-compose.yml
│   ├── .env
│   └── nginx.conf
├── uploads/
├── artifacts/
└── MLM/
```

第一种更适合中长期维护，第二种更适合快速起步。

## 7. Volume 与持久化设计

### 7.1 需要持久化的内容

Compose 方案中至少应持久化以下内容：

- MySQL 数据目录
- Redis 数据目录
- 上传文件目录
- 主动学习与训练产物目录
- 模型目录
- 可选日志目录

### 7.2 推荐卷划分

建议划分为以下几类：

| 卷 / 挂载点 | 作用 |
| --- | --- |
| `mysql-data` | 持久化业务数据库 |
| `redis-data` | 持久化 Redis 数据 |
| `uploads-data` | 保存导入文件与运行时上传内容 |
| `artifacts-data` | 保存训练产物、主动学习中间结果、运行缓存 |
| `model-data` | 保存 embedding 模型或训练模型目录 |
| `logs-data` | 保存可选的容器外日志 |

### 7.3 特别说明

#### 模型目录不要打进镜像

模型目录通常体积较大，且更新频率、来源与业务代码不同步。建议：

- 将模型作为宿主机独立目录挂载
- 容器内统一使用稳定路径引用

这样做可以避免：

- 镜像过大
- 模型更新必须重新打包应用镜像
- 发布时传输成本过高

## 8. 环境变量设计

### 8.1 设计原则

所有部署配置都应通过环境变量注入，原则是：

- 换机器时只改 `.env`
- 容器内统一使用 Linux 路径
- 服务间访问使用 Compose 服务名，而不是 `127.0.0.1`

### 8.2 推荐核心变量

```env
APP_ENV=prod
APP_DEBUG=false
ENABLE_DOCS=false
API_V1_PREFIX=/api/v1

DATABASE_URL=mysql+pymysql://ttt_user:strong_password@mysql:3306/ttt_prod
REDIS_URL=redis://redis:6379/0
CELERY_BROKER_URL=redis://redis:6379/1
CELERY_RESULT_BACKEND=redis://redis:6379/2

IMPORT_UPLOAD_DIR=/data/uploads/imports
EMBEDDING_MODEL_PATH=/data/models/math_mlm_model
ACTIVE_LEARNING_CHECKPOINT_DIR=/data/artifacts/active_learning
```

### 8.3 当前项目中的关键调整方向

基于当前代码结构，部署时需要特别注意以下转化：

- 本地 Windows 盘符路径要改为容器内挂载路径
- 前端开发代理地址不再作为生产访问方式
- 后端的数据库、Redis 地址统一改为服务名访问

也就是说，当前诸如 `C:/Users/...`、`D:/...` 一类路径，在 Compose 方案中都应被替换为稳定的容器内路径。

## 9. Dockerfile 设计思路

### 9.1 backend / worker 共用镜像

建议 backend 与 worker 共用一份镜像，原因是：

- 两者依赖基本一致
- 代码库完全一致
- 只需通过不同启动命令区分功能

推荐镜像构建思路：

1. 使用 Python 3.11 基础镜像
2. 安装必要系统依赖
3. 拷贝 `backend/` 代码
4. 安装 Python 依赖
5. 设置工作目录
6. 默认命令在 Compose 中覆盖

### 9.2 frontend 构建镜像

前端镜像可以有两种设计：

#### 方案 A：独立构建

- 在发布脚本或本地构建 `dist`
- Nginx 容器直接读取该产物

#### 方案 B：多阶段构建

- 第一阶段用 Node 镜像构建前端
- 第二阶段用 Nginx 镜像承载构建产物

当前阶段优先推荐方案 A，后续如需简化发布链路，再收敛到方案 B。

## 10. Docker 网络设计

### 10.1 网络原则

整个 Compose 项目建议使用单独的 bridge 网络，例如：

- `ttt-net`

所有服务均加入该网络：

- `nginx`
- `backend`
- `worker`
- `mysql`
- `redis`

### 10.2 服务间访问方式

在该网络内，各服务通过 Compose 服务名访问：

- backend 访问 MySQL：`mysql`
- backend 访问 Redis：`redis`
- Nginx 转发 backend：`backend:8000`

这样做可以避免对宿主机 IP 和端口绑定产生不必要依赖。

## 11. 启动顺序与健康检查

### 11.1 逻辑启动顺序

从依赖关系上看，建议按以下顺序理解整个系统启动：

1. `mysql`
2. `redis`
3. `backend`
4. `worker`
5. `nginx`

### 11.2 健康检查建议

虽然 Compose 的 `depends_on` 可以表达依赖顺序，但它不能完全保证服务已真正就绪。因此建议：

- 给 MySQL 增加健康检查
- 给 Redis 增加健康检查
- backend 在启动阶段允许短时间重试
- worker 在依赖不可用时具备重启能力

这可以降低“容器已启动但数据库尚未 ready”导致的异常。

## 12. Nginx 配置设计要点

Nginx 在本方案中的配置要点主要有三类：

### 12.1 静态资源服务

- 根路径 `/` 指向前端 `dist`
- 首页加载 `index.html`

### 12.2 API 转发

- `/api/` 转发到 backend
- 保留真实客户端 IP、协议头等常用代理头

### 12.3 SPA 路由回退

对于 `/annotate`、`/annotation-history`、`/admin/overview` 这类前端路由，需要通过回退到 `index.html` 的方式保证浏览器刷新可用。

如果没有这条规则，系统在生产环境下刷新深层路由会直接返回 404。

## 13. 部署流程设计

### 13.1 首次部署流程

推荐首次部署按以下步骤执行：

1. 准备服务器目录
2. 准备 `.env`
3. 安装 Docker 与 Docker Compose
4. 构建 backend 镜像
5. 构建前端产物或前端镜像
6. 启动 `mysql`、`redis`
7. 执行数据库迁移
8. 启动 `backend`、`worker`
9. 启动 `nginx`
10. 验证登录、培训、标注、复核等核心流程

### 13.2 日常发布流程

后续更新版本时，推荐流程如下：

1. 备份数据库
2. 拉取最新代码
3. 重新构建 backend 镜像
4. 执行 Alembic migration
5. 构建前端产物
6. `docker compose up -d`
7. 做冒烟验证

## 14. 冒烟验证建议

部署完成后，应至少验证以下链路：

### 14.1 基础可用性

- 首页可访问
- 登录可用
- 管理员、标注员、复核员三个角色入口正常

### 14.2 标注链路

- 标注员能进入培训页
- 培训通过后能进入标注工作台
- 能领取题目、提交标注
- 能查看个人标注记录

### 14.3 复核链路

- 复核员能领取复核任务
- 能查看多人标注结果
- 能提交最终复核意见

### 14.4 管理链路

- 管理员能查看题池、导入批次、判重复核结果
- 训练页和主动学习页可正常访问

### 14.5 后台任务

- 导入任务可触发
- Worker 能处理至少一类后台任务
- Redis、MySQL 日志中无明显异常

## 15. 本方案的主要优点

采用 Docker Compose 作为第一版部署方案，主要有以下优点：

- 依赖清晰，便于理解现有系统的服务边界
- 一台机器即可较低成本完成多人协作部署
- 迁移到新机器时成本较低
- 上传目录、模型目录、数据库等资产可统一持久化
- 为后续拆分训练节点、补安全机制、接入监控留下空间

## 16. 当前方案的限制与风险

本方案虽然适合第一版部署，但仍需正视当前系统的几个限制：

### 16.1 鉴权与权限安全尚未正式生产化

当前系统更接近受信环境下的开发演示版，后续正式多人长期使用前，仍需重点补齐：

- 正式登录态机制
- 密码哈希存储
- 后端基于当前用户的权限校验
- 默认开发账号治理

### 16.2 训练与标注服务尚未完全分层

虽然 Compose 方案已经将 worker 独立出来，但如果后续训练、embedding 任务持续增多，仍建议将 GPU 或重任务节点进一步拆分。

### 16.3 监控、备份、发布自动化仍需后补

第一版 Compose 方案更多解决“怎么稳定跑起来”，而不是完全解决“怎么规模化运维”。数据库备份、日志聚合、自动化发布等仍应纳入后续阶段。

## 17. 分阶段落地建议

### 17.1 第一阶段：先完成内网多人部署

优先完成：

- Compose 编排
- Nginx 统一入口
- 前端静态部署
- backend / worker 常驻服务
- MySQL / Redis / uploads / models / artifacts 持久化

### 17.2 第二阶段：补生产化安全能力

接着完成：

- 正式鉴权
- 密码加密
- 后端权限收口
- 管理员账号治理
- HTTPS 与访问控制

### 17.3 第三阶段：补运维与扩展能力

最后逐步推进：

- 监控与告警
- 自动化备份
- 发布脚本或 CI/CD
- 训练节点独立部署
- 更细粒度权限体系

## 18. 总结

对于当前 K12 学科标注平台而言，Docker Compose 是最合适的第一版部署方案：它足以承接“从本地开发版切换到多人协作服务版”的核心需求，同时不会过早引入过于复杂的基础设施。

本方案建议将系统拆分为 `nginx + backend + worker + mysql + redis` 五类核心服务，并通过统一网络、统一环境变量和持久化卷管理代码、数据、模型和上传资产。这样可以在较短时间内完成内网部署，并为后续正式生产化改造留下稳定的结构基础。

下一步建议在本方案基础上继续细化：

- `docker-compose.yml` 结构草案
- `backend` 与 `worker` 的 Dockerfile 设计
- Nginx 配置草案
- 部署环境变量清单
- 上线前检查与冒烟验证清单
