# V7 服务器部署操作手册

更新时间：`2026-05-15`

## 1. 手册目的

本文档用于指导 K12 学科标注平台在一台新的 Linux 服务器上完成第一版 Docker Compose 部署，目标是让部署人员按固定步骤完成：

- 服务器目录准备
- Docker 环境准备
- 前端构建产物准备
- Compose 配置准备
- 数据库迁移
- 服务启动
- 部署后验证

本文档默认读者已经拥有服务器登录权限，并能执行 `sudo`。

## 2. 适用范围

## 3. 部署前提

开始部署前，请先确认：

- 目标服务器为 Linux，建议 Ubuntu 22.04 或同类发行版
- 已安装 Git
- 已安装 Docker Engine
- 已安装 Docker Compose 插件
- 服务器能访问代码仓库
- 已准备模型目录内容
- 已确认部署是内网访问还是带域名访问

如果仅用于内网测试，当前阶段可以先使用 HTTP；后续再补 HTTPS。

## 4. 推荐服务器规格

### 4.1 最小建议

如果只承接少量多人标注与基础后台任务，建议：

- 8 vCPU
- 16 GB RAM
- 200 GB SSD

### 4.2 如果训练任务也放在同机

如果还要在同一台机器上跑 embedding、主动学习或训练任务，建议：

- 更高 CPU
- 更大内存
- 更大磁盘
- 或直接把训练任务拆到单独节点

第一阶段建议优先保证标注主服务稳定，再考虑重任务拆分。

## 5. 服务器目录准备

### 5.1 创建目录

在服务器上准备统一目录，例如：

```bash
sudo mkdir -p /opt/ttt/uploads
sudo mkdir -p /opt/ttt/artifacts
sudo mkdir -p /opt/ttt/models
sudo mkdir -p /opt/ttt/logs
sudo mkdir -p /opt/ttt/mysql
sudo mkdir -p /opt/ttt/redis
sudo mkdir -p /opt/ttt/frontend-dist
```

### 5.2 授权建议

建议将这些目录的所有权调整为当前部署用户或一个统一运维用户，避免后续挂载后容器无法写入。

例如：

```bash
sudo chown -R $USER:$USER /opt/ttt
```

如果后续由专用运维账号执行，可替换为对应用户名。

## 6. 安装 Docker 与 Compose

如果服务器还未安装 Docker，可按官方方式安装。安装完成后先验证以下命令：

```bash
docker --version
docker compose version
```

若当前用户无权限运行 Docker，可执行：

```bash
sudo usermod -aG docker $USER
```

然后重新登录 shell。

## 7. 拉取代码

建议把代码仓库放到一个固定目录，例如：

```bash
cd /opt
git clone <your-repo-url> ttt-app
cd /opt/ttt-app
```

如果仓库已经存在，则更新：

```bash
cd /opt/ttt-app
git pull
```

下文默认项目路径为：

```text
/opt/ttt-app
```

## 8. 准备模型与上传路径

### 8.1 模型目录

将当前项目所需的 embedding 模型复制到：

```text
/opt/ttt/models/
```

确保模型最终路径与 `.env` 中的 `EMBEDDING_MODEL_PATH` 对应。

例如当 `.env` 写为：

```env
EMBEDDING_MODEL_PATH=/data/models/math_mlm_model
```

则宿主机上应存在：

```text
/opt/ttt/models/math_mlm_model
```

### 8.2 上传目录

上传目录不需要预先放入业务文件，但需要保证容器有写权限。

## 9. 准备 Compose 配置

### 9.1 复制环境变量模板

进入 Compose 目录：

```bash
cd /opt/ttt-app/deploy/compose
cp .env.example .env
```

### 9.2 修改 `.env`

至少要检查并修改以下内容：

- `MYSQL_PASSWORD`
- `MYSQL_ROOT_PASSWORD`
- `DATABASE_URL`
- `HOST_UPLOADS_DIR`
- `HOST_ARTIFACTS_DIR`
- `HOST_MODELS_DIR`
- `HOST_MYSQL_DIR`
- `HOST_REDIS_DIR`
- `HOST_FRONTEND_DIST_DIR`
- `EMBEDDING_MODEL_PATH`

如果部署目录与本文档推荐目录一致，宿主机路径可以直接沿用模板。

### 9.3 环境变量核对重点

请重点确认：

- `DATABASE_URL` 中的数据库用户名、密码、库名与 MySQL 初始化变量一致
- `EMBEDDING_MODEL_PATH` 指向容器内路径，而不是宿主机路径
- `HOST_FRONTEND_DIST_DIR` 对应的宿主机目录已存在

## 10. 构建前端产物

当前第一版部署方案默认前端产物在宿主机构建后，再挂载给 Nginx。

### 10.1 进入前端目录

```bash
cd /opt/ttt-app/frontend
```

### 10.2 安装依赖

```bash
npm install
```

### 10.3 执行构建

```bash
npm run build
```

### 10.4 复制构建产物

将 `dist` 内容同步到 `.env` 中配置的前端静态目录，例如：

```bash
rsync -av --delete /opt/ttt-app/frontend/dist/ /opt/ttt/frontend-dist/
```

执行后可简单检查：

```bash
ls /opt/ttt/frontend-dist
```

应至少看到 `index.html` 和静态资源目录。

## 11. 构建后端镜像

进入 Compose 目录：

```bash
cd /opt/ttt-app/deploy/compose
```

执行镜像构建：

```bash
docker compose --env-file .env build backend worker migrate
```

如需连同 Nginx 相关镜像一起准备，也可以执行：

```bash
docker compose --env-file .env build
```

## 12. 启动基础服务

### 12.1 启动 MySQL 与 Redis

```bash
docker compose --env-file .env up -d mysql redis
```

### 12.2 查看状态

```bash
docker compose --env-file .env ps
```

### 12.3 查看日志

如果服务未 healthy，可查看：

```bash
docker compose --env-file .env logs mysql
docker compose --env-file .env logs redis
```

确认 MySQL 和 Redis 均正常后再继续。

## 13. 执行数据库迁移

首次部署或版本升级前，需要执行 Alembic migration。

在 Compose 目录执行：

```bash
docker compose --env-file .env --profile tools run --rm migrate
```

如果迁移成功，应看到 `upgrade head` 正常执行完成。

如果失败，优先检查：

- `.env` 中的数据库配置
- MySQL 是否已 healthy
- 镜像是否构建成功

## 14. 启动业务服务

### 14.1 启动 backend 与 worker

```bash
docker compose --env-file .env up -d backend worker
```

### 14.2 查看状态

```bash
docker compose --env-file .env ps
```

### 14.3 查看日志

如需检查启动情况：

```bash
docker compose --env-file .env logs backend
docker compose --env-file .env logs worker
```

重点关注：

- backend 是否成功连上 MySQL / Redis
- worker 是否成功注册并启动 Celery

## 15. 启动 Nginx

当前端构建产物、backend 和 worker 都已就绪后，启动 Nginx：

```bash
docker compose --env-file .env up -d nginx
```

查看状态：

```bash
docker compose --env-file .env ps
```

如 Nginx 异常，优先检查：

- `/opt/ttt/frontend-dist` 是否存在 `index.html`
- `default.conf` 是否挂载成功
- backend 是否已 healthy

## 16. 部署后验证

### 16.1 基础验证

在浏览器访问：

```text
http://<server-ip>/
```

应能正常打开前端首页。

### 16.2 API 验证

可以直接测试健康检查接口：

```bash
curl http://<server-ip>/api/v1/system/health
```

应返回健康状态响应。

### 16.3 登录验证

使用当前系统中的测试账号验证登录页与角色入口：

- 管理员
- 标注员
- 复核员

### 16.4 业务链路验证

建议至少验证：

- 培训页能打开
- 标注页能打开
- 复核页能打开
- 管理后台能打开
- 题池列表能加载
- 异步任务至少能触发一类

## 17. 常用运维命令

### 17.1 查看服务状态

```bash
docker compose --env-file .env ps
```

### 17.2 查看全部日志

```bash
docker compose --env-file .env logs
```

### 17.3 查看单个服务日志

```bash
docker compose --env-file .env logs backend
docker compose --env-file .env logs worker
docker compose --env-file .env logs mysql
docker compose --env-file .env logs redis
docker compose --env-file .env logs nginx
```

### 17.4 重启单个服务

```bash
docker compose --env-file .env restart backend
```

### 17.5 停止全部服务

```bash
docker compose --env-file .env down
```

注意：`down` 不会删除宿主机挂载目录中的数据，但会停止并删除容器。

## 18. 升级发布步骤

系统后续版本升级时，建议按以下顺序操作：

1. 备份数据库
2. 拉取最新代码
3. 如前端有改动，重新执行前端构建并同步 `dist`
4. 重新构建 backend / worker 镜像
5. 执行数据库迁移
6. 重启 backend、worker、nginx
7. 做一次冒烟验证

示例流程：

```bash
cd /opt/ttt-app
git pull

cd /opt/ttt-app/frontend
npm install
npm run build
rsync -av --delete /opt/ttt-app/frontend/dist/ /opt/ttt/frontend-dist/

cd /opt/ttt-app/deploy/compose
docker compose --env-file .env build backend worker migrate
docker compose --env-file .env --profile tools run --rm migrate
docker compose --env-file .env up -d backend worker nginx
```

## 19. 常见问题排查

### 19.1 页面能打开，但刷新某个页面 404

优先检查 Nginx 的 `try_files` 是否生效，以及是否使用了仓库中的：

- [deploy/docker/nginx/default.conf](C:/Users/29694/Desktop/ttt/deploy/docker/nginx/default.conf)

### 19.2 页面空白或静态资源 404

优先检查：

- `/opt/ttt/frontend-dist` 是否存在构建产物
- `HOST_FRONTEND_DIST_DIR` 是否正确
- Nginx 是否成功挂载静态目录

### 19.3 backend 启动失败

优先检查：

- `DATABASE_URL`
- `REDIS_URL`
- MySQL / Redis 是否 healthy
- 模型路径是否存在

### 19.4 worker 启动失败

优先检查：

- `CELERY_BROKER_URL`
- `CELERY_RESULT_BACKEND`
- Redis 是否 healthy
- backend 镜像是否已正确构建

### 19.5 迁移失败

优先检查：

- MySQL 是否正常启动
- `.env` 中数据库库名、用户、密码是否一致
- 迁移命令是否在 `deploy/compose` 目录执行

## 20. 当前手册的边界

本手册解决的是“如何把当前系统部署到一台 Linux 服务器并稳定跑起来”，不等同于已经完成以下事项：

- 正式生产级鉴权
- 密码哈希改造
- HTTPS 证书接入
- 监控告警
- 自动化备份
- 公网暴露前的安全收口

这些内容仍建议作为二阶段继续推进。
