# V4.5 嵌入可视化与复核闭环实现

## 1. 文档目的

本文档用于记录 V4.5 阶段新增和调整的功能，重点说明本轮工作如何补齐以下能力：

- 题目导入后生成 Roberta 嵌入向量
- 系统维护全量题目的 embedding 矩阵
- 管理员在可视化页面查看题目二维分布
- 一键补全历史题目的缺失嵌入
- 复核员只处理复核任务，不再参与普通标注
- 标注聚合出现分歧后，复核员可领取待复核题并提交最终结果

V4.5 的目标不是新增一组孤立页面，而是把“题目表示、主动学习可视化、标注质量复核”三条链路连接起来，为后续训练闭环提供更稳定的数据基础。

## 2. 本阶段业务定位

在 V4 之前，系统已经具备：

- 题库导入
- 题目判重与人工判重复核
- 管理员 CoreSet 选题
- 标注员领取和提交标注
- 三人标注后生成聚合结果
- 有分歧时进入待复核池
- 标注员培训准入

但仍有几个关键缺口：

1. CoreSet 和可视化没有稳定的真实语义向量支撑。
2. `/visualization` 页面仍停留在占位状态。
3. 历史题库缺少批量补全 embedding 的入口。
4. 复核员角色边界不清晰，仍能进入普通标注工作台。
5. 标注分歧虽然会生成 `review_tasks`，但缺少复核员领取和提交最终结论的闭环。

因此 V4.5 聚焦两个主线：

- **语义表示与可视化主线**：用本地 Roberta 模型生成题目 embedding，并基于降维结果展示题库分布。
- **复核闭环主线**：将复核员从普通标注中剥离出来，只处理判重复核和标注分歧复核。

## 3. 嵌入向量能力

### 3.1 模型来源

本阶段接入本地预训练 Roberta 模型：

- 默认路径：`E:/zhuanli/rePretrain/math_mlm_model`
- 默认模型编码：`math-roberta-mlm-v1`
- 默认模型名称：`Math Roberta MLM`

对应配置项位于：

- `backend/app/core/config.py`

新增配置：

- `EMBEDDING_MODEL_PATH`
- `EMBEDDING_MODEL_CODE`
- `EMBEDDING_MODEL_NAME`
- `EMBEDDING_BATCH_SIZE`
- `VISUALIZATION_MAX_POINTS`

### 3.2 依赖补充

后端新增依赖位于：

- `backend/pyproject.toml`

新增依赖包括：

- `torch`
- `transformers`
- `safetensors`
- `numpy`
- `scikit-learn`

其中：

- `torch / transformers / safetensors` 用于加载 Roberta 并生成题目向量
- `numpy / scikit-learn` 用于 PCA / t-SNE 等降维计算

### 3.3 模型加载策略

模型加载由：

- `backend/app/services/embedding_service.py`

负责。

实现中使用 `lru_cache(maxsize=1)` 缓存本地模型组件：

- 第一次生成 embedding 时加载 tokenizer 和 model
- 同一个后端进程内后续复用内存中的模型
- 后端进程重启或代码热重载后才会重新加载

这意味着：

- 可视化刷新不会重复加载 Roberta
- 查询已有 embedding 不会调用 Roberta
- 只有生成缺失 embedding 时才会调用模型

### 3.4 向量生成方式

当前题目向量输入由以下文本拼接得到：

- 题干 `stem_text`
- 答案 `answer_text`
- 解析 `solution_text`

模型输出后采用 mean pooling：

1. 获取 `last_hidden_state`
2. 使用 attention mask 过滤 padding
3. 对有效 token 做平均池化
4. 对最终向量做 L2 normalize
5. 写入 `question_embeddings.vector_json`

当前向量维度从模型 `config.json` 中读取，默认兜底为 `768`。

### 3.5 数据库存储

本阶段复用已有数据库结构，不新增迁移。

核心表：

- `embedding_models`
- `question_embeddings`
- `questions.latest_embedding_version`

每道题的向量作为一行 `question_embeddings` 记录保存：

- `question_id`
- `embedding_model_id`
- `vector_json`
- `vector_norm`
- `computed_at`

系统意义上的“全量 embedding 矩阵”不是额外保存为单独文件，而是由 `question_embeddings` 表按当前 active model 组装为 `N x D` 矩阵。

## 4. 导入流程中的 embedding 维护

导入流程接入点位于：

- `backend/app/services/import_service.py`

本阶段新增行为：

- 新建题目后尝试生成 embedding
- 导入记录匹配到已有题目后，也尝试确保该题存在 embedding
- embedding 生成失败不会中断导入流程

这样设计的原因是：

- 导入是主业务流程，不应被模型环境问题阻塞
- Roberta 依赖或模型路径异常时，系统仍能导入题目
- 管理员可后续通过“一键补全嵌入”补齐缺失数据

## 5. 一键补全嵌入

### 5.1 后端接口

新增接口位于：

- `backend/app/api/v1/visualization.py`

相关接口：

- `GET /api/v1/visualization/embedding-status`
- `POST /api/v1/visualization/embeddings/rebuild`

`embedding-status` 返回：

- 模型编码
- 模型名称
- 模型维度
- 模型路径
- 模型是否可用
- 总题目数
- 已有 embedding 数
- 缺失 embedding 数

`embeddings/rebuild` 支持传入 `limit`，用于每次补全一批缺失题目的 embedding。

### 5.2 批量生成优化

早期实现是逐题调用模型。

V4.5 已调整为批量编码：

- 一次查询一组缺失题目
- 使用 tokenizer 批量 padding/truncation
- 一次模型 forward 生成一批向量
- 再逐题写入数据库

默认批大小由 `EMBEDDING_BATCH_SIZE` 控制。

### 5.3 前端一键补全

前端页面：

- `frontend/src/pages/visualization/index.tsx`

新增“一键补全嵌入”按钮。

交互方式：

1. 用户点击一次按钮
2. 前端循环读取当前缺失数量
3. 每轮调用一次后端批量补全接口
4. 更新进度条、已补全数量、失败数量和批次数
5. 缺失数量归零或后端不再新增时结束

采用“前端循环 + 后端批处理”的原因：

- 避免一次超长 HTTP 请求
- 便于显示进度
- 中途失败时可以保留已完成结果
- 后续可以较自然地升级为后台任务队列

## 6. 可视化页面

### 6.1 页面入口

页面路径：

- `/visualization`

文件位置：

- `frontend/src/pages/visualization/index.tsx`

该页面从原占位页升级为真实可用的题库可视化页面。

### 6.2 后端数据接口

新增接口：

- `GET /api/v1/visualization/question-distribution`

支持参数：

- `method=pca|tsne|umap`
- `status=all|PENDING|WAITING|IN_PROGRESS|REVIEW_PENDING|COMPLETED`
- `limit`

返回内容：

- 实际使用的降维方法
- 请求的降维方法
- 当前模型编码
- 已绘制点数
- 缺失 embedding 数
- 各状态数量统计
- 二维点位列表

点位包括：

- `question_id`
- `x`
- `y`
- `annotation_status`
- `annotation_count`
- `required_annotations`
- `stem_preview`

### 6.3 降维策略

当前支持：

- `PCA`
- `t-SNE`
- `UMAP`

其中：

- `PCA` 是默认策略，适合快速刷新全量或大规模数据
- `t-SNE` 适合观察局部聚类，但在大规模数据时成本更高
- `UMAP` 预留支持，如果运行环境未安装对应依赖则自动回退

当目标方法不可用时，系统会自动回退到可用方法，确保页面不会因降维依赖缺失而不可用。

### 6.4 状态颜色

可视化散点按题目状态着色：

- `PENDING`：未标注
- `WAITING`：待标注
- `IN_PROGRESS`：标注中
- `REVIEW_PENDING`：待复核
- `COMPLETED`：已完成

页面支持：

- 状态筛选
- 降维方式切换
- 刷新图表
- 缩放和拖拽
- 点击散点查看题目详情
- 显示全局统计和选中题目详情

## 7. 复核员角色调整

### 7.1 角色边界

V4.5 明确复核员角色职责：

- 可以处理判重复核
- 可以处理标注分歧复核
- 不再参与普通标注

因此本阶段做了两层限制。

### 7.2 前端限制

路由文件：

- `frontend/src/router/index.tsx`

侧边栏文件：

- `frontend/src/layouts/AppShell/index.tsx`

调整后：

- `/annotate` 仅允许 `annotator` 访问
- 复核员侧边栏不再显示“标注工作台”
- 复核员新增“标注复核”入口 `/review`

### 7.3 后端限制

普通标注接口增加角色校验：

- `POST /api/v1/annotations/claim`
- `POST /api/v1/annotations/tasks/{task_id}/submit`

只有 `role.code = annotator` 的用户才能领取和提交普通标注任务。

复核员直接调用普通标注接口会返回：

- `403 Forbidden`

这样避免只依赖前端隐藏菜单造成越权调用。

## 8. 标注分歧复核闭环

### 8.1 触发条件

三人标注后系统会聚合结果。

聚合逻辑位于：

- `backend/app/services/annotation_service.py`

当出现以下情况时，题目进入待复核：

- 认知层级投票不一致
- 核心素养等级投票不一致

系统会：

- 设置 `questions.annotation_status = REVIEW_PENDING`
- 设置 `question_label_aggregates.is_disputed = true`
- 创建 `review_tasks` 记录
- `review_tasks.review_status = PENDING`

### 8.2 复核任务表

复用已有表：

- `review_tasks`

关键字段：

- `question_id`
- `aggregate_id`
- `reviewer_id`
- `review_status`
- `review_comment`
- `created_at`
- `reviewed_at`

状态流转：

1. `PENDING`
2. `IN_PROGRESS`
3. `COMPLETED`

### 8.3 后端复核接口

新增接口：

- `POST /api/v1/annotations/review-tasks/claim`
- `GET /api/v1/annotations/review-tasks`
- `POST /api/v1/annotations/review-tasks/{review_task_id}/submit`

接口职责：

- `claim`：复核员从待复核池领取任务
- `list`：复核员查看自己已领取的复核任务
- `submit`：提交最终复核结论

提交复核后系统会：

- 更新聚合结果
- 将 `is_disputed` 置为 `false`
- 重写最终核心素养矩阵
- 设置 `review_tasks.review_status = COMPLETED`
- 记录 `reviewer_id / reviewed_at / review_comment`
- 设置 `questions.annotation_status = COMPLETED`

### 8.4 前端复核页面

新增页面：

- `frontend/src/pages/review/index.tsx`

页面路径：

- `/review`

页面能力：

- 领取复核题
- 查看我的复核任务
- 查看题干
- 查看三位标注员提交结果
- 查看当前聚合结果和一致率
- 填写最终核心素养矩阵
- 填写复核说明
- 提交复核结论

复核员在这里做的是“标注检查和最终裁决”，不是普通标注员意义上的新增一票。

## 9. 判重复核与标注复核的区别

当前系统中有两类复核：

### 9.1 判重复核

入口：

- `/dedup-review`

处理对象：

- `question_duplicate_candidates`

解决问题：

- 新导入题目是否与已有题目重复

操作结果：

- 确认重复：挂接到已有题
- 确认不重复：物化为新题

### 9.2 标注分歧复核

入口：

- `/review`

处理对象：

- `review_tasks`

解决问题：

- 三位标注员结果不一致时，最终标签如何确定

操作结果：

- 更新聚合标签
- 完成复核任务
- 题目进入 `COMPLETED`

两者都由复核员承担，但业务对象和数据表不同。

## 11. 当前限制与后续建议

### 11.1 embedding 生成限制

当前一键补全嵌入由前端循环触发，已经可用，但仍有升级空间：

- 可改为后端后台任务
- 可增加任务进度表
- 可支持暂停、继续、失败重试
- 可避免浏览器关闭后任务中断

### 11.2 可视化性能限制

当前可视化直接从数据库读取 embedding 并即时降维。

后续可优化：

- 缓存 PCA/UMAP 投影结果
- 增加投影版本表
- 对大规模数据做抽样预览
- 前端使用分层渲染或 WebGL scatter

### 11.3 复核审计限制

当前复核结果写回聚合表和 `review_tasks`，但还没有单独的复核历史明细表。

后续建议：

- 新增 `review_decisions`
- 保存复核前聚合结果
- 保存复核员最终矩阵
- 支持回滚和审计追踪

### 11.4 权限体系限制

当前后端通过显式角色校验限制普通标注和复核任务。

后续可继续升级：

- 接入真实鉴权 token
- 后端从登录态获取 user_id，而不是由前端传 user_id
- 对 admin 是否可代复核做明确策略
- 对接口补充统一 RBAC 中间件

## 12. 当前结论

V4.5 阶段使系统从“标注流程可跑通”进一步升级为：

- 题目具备真实语义向量表示
- CoreSet 和可视化具备统一 embedding 基础
- 管理员可以查看题库分布
- 历史题库可以一键补全嵌入
- 复核员角色边界清晰
- 标注分歧可以进入复核闭环并最终完成

这为下一阶段的主动学习训练闭环奠定了更完整的基础。
