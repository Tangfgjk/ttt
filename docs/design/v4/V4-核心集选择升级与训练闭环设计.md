# V4 核心集选择升级与训练闭环设计

## 1. 文档目的

本文档用于总结当前核心集选择实现的现状与限制，并给出面向正式训练阶段的升级思路。重点回答三个问题：

- 当前代码里的核心集选择适合什么阶段
- 为什么正式训练不能长期停留在“只看前 600/2000 题”
- 后续应该如何升级为“全量未标注池参与决策”的主动学习闭环

## 2. 当前实现定位

当前系统已具备可运行的核心集选择原型，核心策略包括：

- `random`
- `kmeans`
- `facility_location`
- `graph_cut`
- `moe`

现有代码实现位置：

- 算法选择器：`backend/app/services/coreset_selection.py`
- 业务调度入口：`backend/app/services/annotation_service.py`

当前流程是：

1. 从 `questions` 表中加载 `annotation_status = PENDING` 的未标注题
2. 根据选择策略确定候选池上限
3. 优先使用现有 embedding；若无 embedding，则退化为基于题干文本的哈希向量
4. 在候选池内运行核心集选择算法
5. 将选中的题从 `PENDING` 推进到 `WAITING`
6. 标注员后续从 `WAITING` 池中领题

这套实现已经足以支撑：

- 推荐批次生成
- 不同策略的可运行验证
- 标注池调度联调
- 题目从“未进入标注”到“进入待领取”的业务流转

## 3. 当前实现的限制

### 3.1 候选池是截断的，不是全池决策

当前策略在进入算法前，会先截取一个有限候选池：

- `facility_location / graph_cut / moe` 最多处理 `600` 题
- `kmeans / random` 最多处理 `2000` 题

这意味着当前算法并不是在完整未标注池上做选择，而是在“候选子集”上做选择。对于原型联调这是合理的，但对于正式训练阶段不够。

### 3.2 当前限制的本质是算力保护

之所以存在 `600 / 2000` 的上限，不是业务上只需要看这么多题，而是因为：

- `facility_location` 和 `graph_cut` 需要频繁计算样本之间的相似度
- `moe` 本质上又组合了多次选择过程
- 当未标注池扩大到几万、几十万题后，直接全量精确计算会明显变慢

因此，当前实现更适合：

- 原型阶段
- 小规模题池
- 流程联调
- 算法对比实验

而不适合作为最终训练闭环的长期方案。

### 3.3 当前 embedding 仍有兜底方案

当前选择器在没有真实向量时，会用题干文本构造哈希向量。这个设计有助于系统在 embedding 管线未完成前先运行起来，但它的表示能力弱于正式语义向量，因此更适合原型阶段，而不是最终生产策略。

## 4. 正式训练阶段的目标

正式训练阶段的核心要求不是“暴力对全量题做一次精确计算”，而是：

**让完整未标注池都参与决策，但通过分层和近似方式控制计算成本。**

因此，后续方案应从“局部子集选择”升级为：

**全池参与决策 + 分层过滤 + 粗筛 + 精排 + 回流训练**

## 5. 推荐升级方案

### 5.1 第一层：全量题目向量化

要让全池参与决策，前提是未标注池中的题目尽量都具备稳定 embedding。建议后续为每道题构建统一向量，输入可包括：

- 题干文本
- 选项文本
- 图片 OCR 文本
- 题型信息
- 学段信息
- 章节或知识点信息

这样后续的相似度、聚类、代表性评估才有一致的基础。

### 5.2 第二层：先做业务分桶，不要混池硬选

在本项目中，题目天然存在明显分层，因此不建议把所有未标注题混成一个池直接选。建议先按业务维度分桶，再在桶内做预算分配与样本选择，例如：

- 学段：初中 / 高中
- 年级：七年级到高三
- 题型：选择、填空、解答
- 章节 / 知识点
- 是否属于长尾类别
- 当前模型的不确定性区间

这样可以保证：

- 不同学段不会互相挤占预算
- 年级分布更均衡
- 后续训练集覆盖更合理
- 核心素养体系不会跨学段混淆

### 5.3 第三层：全池粗筛

正式方案不建议直接在全量未标注池上跑精确 `facility_location` 或 `graph_cut`，而是先做粗筛，将候选池从全量压缩到一个可计算规模。

粗筛可以使用以下一种或多种方式：

- 基于业务分桶后的分层抽样
- 基于聚类的簇级候选保留
- 基于向量索引的近邻覆盖采样
- 基于模型不确定性的高价值样本初筛
- 基于长尾标签与低频章节的补偿采样

粗筛后的候选规模可以根据实际算力设置，例如：

- `全量未标注池 -> 3000 ~ 10000 候选`

关键点不是固定数字，而是：

- 候选应来自完整未标注池
- 候选应体现业务分布与模型需求

### 5.4 第四层：局部精排

在粗筛后的候选集上，再运行真正的核心集选择策略，例如：

- `kmeans`：保证簇级覆盖
- `facility_location`：提升全局代表性
- `graph_cut`：降低冗余并保持多样性
- `moe`：组合多种策略

这一步仍然是核心集选择的核心，但它不再直接面对整个未标注池，而是面对“经过全池决策得到的高质量候选集”。

这样既保留了算法效果，也把计算成本控制在可接受范围内。

## 6. 与主动学习结合的方向

正式训练阶段不建议只看“代表性”，而应该将核心集选择和主动学习结合起来。每道题的综合优先级可以由以下几个信号共同决定：

- 代表性：能否代表一片未标注区域
- 多样性：是否避免和已选题过于重复
- 不确定性：模型是否对该题判断不稳定
- 长尾补偿：是否来自低频年级、知识点或素养模式

因此，后续系统可设计一个综合评分，而不是长期依赖单一算法：

`总分 = a * 不确定性 + b * 代表性 + c * 多样性 + d * 长尾补偿`

其中系数可按阶段动态调整。

## 7. 推荐演进阶段

### 7.1 当前阶段：保留轻量原型

当前代码应继续承担：

- 推荐流程联调
- 选择策略对比
- 标注池调度验证

在这一阶段，不需要追求完整训练闭环，但要保留后续扩展接口。

### 7.2 中期阶段：升级为“全池粗筛 + 局部精排”

建议在这一阶段补齐：

- 题目 embedding 计算与落库
- 向量索引
- 业务分桶与预算分配
- 候选粗筛服务
- 精排服务

这一阶段的目标是让“完整未标注池参与决策”真正落地。

### 7.3 正式训练阶段：建立闭环

当数据、标注与模型训练都稳定后，核心集选择应进入真正的主动学习闭环：

1. 全量未标注池分桶
2. 模型对全池推理
3. 生成不确定性与业务特征
4. 粗筛形成候选池
5. 精排生成推荐批次
6. 人工标注回流
7. 新模型训练
8. 效果评估
9. 进入下一轮

## 8. 本项目中的推荐落地顺序

结合当前项目现状，建议按以下顺序推进：

1. 先补齐学段路由，确保初中题和高中题在标注与推荐层面隔离
2. 为题目补齐稳定 embedding 管线
3. 为未标注池建立按学段、年级、题型的分桶能力
4. 在分桶基础上实现粗筛层
5. 保留现有 `kmeans / facility_location / graph_cut / moe` 作为精排层
6. 将标注结果回流到训练批次与效果评估中
7. 最终形成主动学习闭环

## 9. 当前结论

当前代码里的核心集选择实现是一个合理的第一版原型，但它的设计目标是“让流程跑起来”，不是最终训练方案。

后续真正可扩展的方向应当是：

- 不是只在一个固定小候选池里挑题
- 也不是直接对全量题暴力精算
- 而是让完整未标注池通过分层、粗筛、精排的方式参与决策

这将使核心集选择从“推荐功能”升级为“训练闭环中的调度中枢”。
